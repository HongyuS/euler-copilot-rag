# 查找技能（Find）

## 目标

为创建/优化/合并提供依据。**查重**与**发现更多技能**必须拆开：**查重只使用当前已激活（本会话可用）的技能列表**；生态检索只在用户明确要“找更多/安装”时使用。

## 触发条件

- 用户问“有没有能做 X 的 skill”
- 创建前查重
- 合并前盘点
- 任务完成后的主动技能化检查（命中后先查重）

## 查重边界（必须遵守）

**查重（dedup）只允许使用唯一信息源：当前已激活的可用技能列表。**

- 以宿主注入的列表为准（例如 `available_skills`、OpenCode 当前会话已加载且允许使用的技能）。通常每条含 `name` + `description`，仅用这两项做相似度与重复判断。
- **禁止**为查重去扫描磁盘、递归查找某目录下的 `SKILL.md`、或把「磁盘上存在但未在本列表中出现」的技能当作重复依据——那些属于**未激活**，对当前会话无效。

**明确禁止（除非用户明确要求）：**

- 使用任何 **RAG / 向量知识库 / 文档库 MCP** 去“查询 skill 名单”或做查重。
- 把 skill 内容、skill 名单、评测产物**写入/导入**到用户的 RAG 知识库（含“索引化”“入库”“同步到知识库”等同类操作）。

若用户明确说“请用某个知识库 MCP 做查重/入库”，才可以使用，且必须在报告中标注为**用户显式授权**。

## 执行步骤

### 步骤 1：理解查询意图

提炼三要素：

1. 领域（前端、测试、文档等）
2. 任务（要完成什么）
3. 约束（查重是否仅看已激活列表、是否允许联网查生态）

### 步骤 2：查重（dedup，仅已激活列表）

仅从当前会话的**已激活技能列表**中取候选，然后做相似度判断：

- 名称/description 是否匹配
- 是否可直接复用
- 是否更适合“优化已有”而非“新建”

**输出要求：**在 `Skill Operation Report` 的「分析」中写明查重依据为「已激活技能列表」，可列出用于比对的 `name`（不得声称从磁盘目录或 RAG 扫出 skill 名单）。

### 步骤 3：生态发现（可选，仅当用户要“找更多/安装”）

仅当用户明确希望从开放生态发现技能时，才执行：

```bash
npx skills find <query>
```

必要时安装：

```bash
npx skills add <owner/repo@skill> -g -y
```

**注意：**生态发现的结果**不得**替代步骤 2 的本地查重结论；它只用于“额外安装候选”。

### 步骤 4：质量校验（仅针对生态候选）

推荐前至少验证：

1. 安装量（优先较高安装量）
2. 来源可信度（官方/知名组织优先）
3. 仓库基础质量（活跃度、口碑）

## 决策输出

返回以下之一：

- 直接复用已有 skill
- 优化已有 skill（跳转 `abilities/optimize-skill.md`）
- 合并已有 skill（跳转 `abilities/merge-skills.md`）
- 创建新 skill（跳转 `abilities/create-skill.md`）

## 注意

仅凭搜索结果不直接推荐；必须完成最小质量校验。
若查找后进入评测与对比阶段，分别转到 `agents/grader.md`、`agents/analyzer.md`、`agents/comparator.md` 获取标准化方法。
